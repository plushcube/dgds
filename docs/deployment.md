# Разворачивание

Сервер поставляется контейнерным образом: слушает только HTTPS с самоподписанным сертификатом и хранит данные в томе.

## Образ

`Dockerfile` в корне репозитория собирается в две стадии. В первой (ubuntu 24.04) собирается `dgds` без тестов (`-DWITH_TESTS=OFF`), номер сборки передаётся аргументом `PATCH_VERSION` и попадает в версию продукта. Во вторую стадию попадают только бинарник и то, что нужно ему для работы: `libssl3` и `curl` для проверки живости. Там же создаётся системный пользователь `dgds` (uid 10001), ему отдаётся каталог данных, и объявляются том `/data` и порт `8443`.

```sh
docker build --tag dgds:local --build-arg PATCH_VERSION=1 .
```

Сборка образа выполняется в CI на Linux-раннере. Релиз `release.yml` пока публикует только пакет `.deb`: образ собирается, но не публикуется, поэтому в реестр его нужно класть отдельно.

## Запуск

```sh
docker volume create dgds-data
docker run --detach --name dgds --publish 127.0.0.1:8443:8443 --volume dgds-data:/data dgds:local
```

То же самое через compose — он описывает сборку из корневого `Dockerfile`, порт, именованный том, проверку живости и перезапуск:

```sh
docker compose up --detach --wait
```

Наружу публикуется только петлевой адрес: сертификат самоподписанный, и выставлять такой сервер в сеть без внешнего терминатора TLS не следует.

## Первый запуск и сертификат

Сертификат сервер выпускает сам при первом запуске в `<каталог данных>/tls` и дальше переиспользует, пока файлы на месте: ключ EC P-256, имена `localhost` и `127.0.0.1`, закрытый ключ записывается с правами владельца. При запуске сервер печатает путь к сертификату, его отпечаток и фактический адрес:

```
Каталог данных:  /data
Сертификат:      /data/tls/server.crt
Отпечаток:       45:de:41:ee:99:e5:97:20:ad:6c:7a:79:c8:e3:2c:0d:2c:1e:8a:64:63:b3:18:34:f7:c8:53:b4:a7:d8:23:8c
Слушаю https://0.0.0.0:8443
```

Строка «Отпечаток» — это SHA-256 по сертификату, а «Закрепление» — SHA-256 по SubjectPublicKeyInfo, то есть ровно то значение, которое закрепляет и печатает клиент. Сравнивать закрепление нужно со второй строкой; сертификат при этом передают клиентам вне канала. Из работающего контейнера его удобно забрать так:

```sh
docker compose cp dgds:/data/tls/server.crt ./server.crt
```

Ротация сертификата и выпуск его удостоверяющим центром вне области работ: чтобы сменить сертификат, файлы `tls/server.crt` и `tls/server.key` удаляют в томе и контейнер перезапускают, после чего новый сертификат заново передают клиентам.

## Проверка живости

Проверка живости — не «порт открыт», а настоящий запрос по HTTPS: `curl` с проверкой сертификата из тома обращается к `/catalog`. Она описана и в образе, и в `compose.yaml` и знает о сервере две вещи, которые нужно править вместе с ним: внутренний порт `8443` и версию протокола в теле запроса (`{"version":1}`). Если переопределить `--port` или поднять версию протокола, проверку надо поправить в обоих файлах, иначе контейнер будет числиться нездоровым при живом сервере. Публикация наружу другого порта этого не требует — достаточно маппинга (`--publish 127.0.0.1:9443:8443`).

## Данные

Размер публикуемого файла ограничен 4 МиБ: предел задан в протоколе и проверяется на сервере, а тело запроса и ответа ограничены согласованно с ним.

В томе `/data` лежат все хранилища и сертификат: `blobs`, `identities`, `keys`, `metadata`, `master.key` и `tls`. Пересоздание контейнера данные не теряет и сертификат не меняет: после `docker compose up --force-recreate` каталог и реестр покупок отвечают теми же записями, а отпечаток сертификата совпадает. Том можно заменить каталогом хоста, но тогда его владельцем должен быть пользователь с uid 10001: контейнер работает без привилегий и в чужие права не влезает.

## Ограничения

Оркестрация вне области работ: разворачивание ограничено одной службой и её композицией. Управление секретами тоже: мастер-ключ хранилища ключей в учебной версии лежит в томе, в целевом продукте его место занимает служба управления ключами.
