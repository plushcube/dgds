# DGDS

Сервис защищённой дистрибуции цифрового контента.

## Описание проекта

Автор публикует файл, покупатель приобретает доступ к нему и получает возможность прочитать содержимое. Контент хранится зашифрованным, ключ расшифровки выдаётся вместе с покупкой и привязан к устройству покупателя: скопированный файл сам по себе бесполезен, а расшифрованный существует только в памяти клиента на время сессии.

Сервис исходит из того, что покупатель может оказаться нарушителем лицензии, поэтому каждый выданный экземпляр отчуждаем: по утёкшей копии можно установить, из какой покупки она произошла. Задача защиты — сделать обход дороже выгоды, а не сделать его невозможным.

В рамках проекта реализуются общая архитектура системы и ядро обработки и дистрибуции файлов. Работа с базой данных, управление доступом и распределённые сервисы заменяются локальными заглушками.

## Термины

- **Контент** — файл, который публикует автор.
- **Каноническая форма** — представление контента, из которого удалён канал служебной метки и приведены к единому виду эквивалентные записи. По ней считаются идентичность, дедуп и размер в каталоге.
- **Идентификатор контента** — отпечаток канонической формы, по которому определяется дубликат.
- **Ключ файла** — ключ, которым зашифрован контент публикации.
- **Ключ покупки** — ключ, создаваемый при покупке; им обёрнут ключ файла в чеке.
- **Чек** — локальный контейнер покупки: идентификатор покупки, идентификатор покупателя, дата покупки, дата выпуска обёртки, обёртка ключа покупки на ключ устройства и версия схемы. Хранится в защищённом хранилище устройства.
- **Пакет** — то, что сервер выдаёт покупателю: зашифрованный контент, обёртка ключа, идентичность контента, подпись автора и версия схемы.
- **Метка** — невидимые символы, встроенные в выдаваемый экземпляр и кодирующие покупку.
- **Устройство** — экземпляр клиента пользователя с собственным ключом, хранимым средствами платформы.

## Функциональные требования

### Пользователи и роли

- server: регистрация нового пользователя по имени, без пароля; при регистрации выдаётся идентификатор пользователя в формате UUID
- server: вход зарегистрированного пользователя выдаёт учётные данные для последующих запросов
- server: любой пользователь может быть автором, то есть публиковать файлы
- server: публикация, покупка, списки пользователя, выпуск копии чека и получение пакета требуют авторизации
- client: просмотр каталога доступен без авторизации

### Просмотр списка доступных к покупке файлов

- client: общая информация о файле (название, имя файла, размер, дата публикации) и авторе (имя)
- client: запрос на покупку доступного файла

### Просмотр списка купленных файлов

- client: общая информация о файле и его авторе
- client: дата покупки

### Просмотр списка опубликованных файлов

- client: общая информация о файле
- client: количество покупок, не считая доступ самого автора

### Публикация авторского файла

- server: проверка на дубликаты по идентификатору канонической формы
- server: при совпадении публикуется первый, второй автор получает ошибку; занятый идентификатор не освобождается
- server: формирование ключа файла и шифрование контента; ключ файла хранится отдельно от шифротекста
- server: цифровая подпись покрывает идентичность канонической формы и имя автора
- server: доступ автора к собственному контенту возникает вместе с публикацией, без покупки

### Покупка файла

- server: формирование покупки с датой и уникального ключа покупки, которым оборачивается ключ файла
- server: привязка чека к ключу устройства покупателя
- server: повторный запрос покупки не создаёт новую покупку и возвращает ранее выпущенный чек
- server: выпуск копии чека для существующей покупки — с новой привязкой к устройству и прежней датой покупки
- client: загрузка и сохранение чека в защищённом хранилище устройства

### Выдача и открытие файла

- server: выдача пакета только владельцу покупки, право проверяется по реестру покупок
- server: в выдаваемый экземпляр встраивается метка с идентификатором покупки
- client: проверка идентичности контента и подлинности подписи автора
- client: расшифровка только в память; открытый текст не записывается на устройство и освобождается после передачи потребителю
- client: передача контента потребителю только после успешных проверок

### Атрибуция утечек

- server: по утёкшей текстовой копии определяется покупка, из которой она произошла, с проверкой целостности метки
- server: результат определения — покупатель, публикация и дата покупки

## Нефункциональные требования

- клиент-серверная архитектура: клиент — библиотека, встраиваемая в приложение пользователя, сервер — отдельный процесс; обмен по HTTP, версия протокола присутствует в каждом запросе и ответе
- поддержка любых файлов-носителей: ядро не зависит от формата, атрибуция применяется там, где для формата определён канал метки
- модульная структура с возможностью замены алгоритмов шифрования: идентификаторы алгоритмов передаются в метаданных, что позволяет менять их без выпуска нового клиента
- возможность использования различных БД: хранилища и реестры описаны портами, реализации заменяемы
- возможность разделения хранилищ: контент, ключи и метаданные размещаются раздельно, ключ файла не хранится вместе с шифротекстом
- параллельная обработка запросов: сервер обслуживает запросы одновременно, а синхронные обращения к хранилищам выполняются на выделенном пуле, поэтому ожидание не блокирует обработку остальных запросов
- сервер не доверяет клиенту: право на выдачу и параметры операций проверяются на стороне сервера

## Модель угроз

| Что защищаем | Чем |
| --- | --- |
| контент в хранилище | шифрование ключом файла, ключи — в отдельном хранилище |
| контент при передаче | TLS с закреплением сертификата, адресная выдача |
| чек и ключ на устройстве | неизвлекаемый ключ устройства, обёртка привязана к устройству и контексту покупки |
| открытый текст на устройстве | расшифровка только в памяти, без записи на диск, с освобождением буфера |
| распространение копий | скопированный шифротекст и чек бесполезны вне устройства, а утёкший открытый текст атрибутируем |

Не защищаемся от:

- владельца устройства с правами администратора: он может исследовать память процесса, поэтому на десктопе защита от копирования недостижима в принципе
- оператора сервиса: он формирует выдачу и хранит базы; подпись автора защищает доставку, а не сервер
- сговора покупателей, сравнивающих свои копии: различия в метках можно вычислить и удалить

Принятые риски:

- аутентификация по имени не является надёжной; в учебной версии управление доступом заменено заглушкой
- канал метки известен клиенту, потому что клиент обязан приводить контент к канонической форме; секретом остаётся только кодирование
- проверка дубликатов сообщает, есть ли такой контент в системе; запросы ограничены по частоте
- расшифрованный контент доступен потребителю, поэтому его дальнейшее распространение не предотвращается, а только атрибутируется

## Что вне скоупа

- реальная база данных, управление доступом и распределённые сервисы: заменяются локальными файлами-заглушками
- аттестация клиентов и управление доверием к сборкам
- блокировка нарушителей и юридические процедуры
- форматозависимые метки и эвристики определения дубликатов: интерфейсы под них закладываются, реализации относятся к целевому продукту
- публикация документации

## Архитектура

Ядро содержит домен и порты и не выполняет ввода-вывода. Клиентская библиотека встраивается в приложение пользователя и обращается к защищённому хранилищу устройства. Серверная библиотека отвечает за обработчики, сценарии и middleware, а приложение связывает реализации портов и запускает сервер. Заглушки внешних сервисов и платформы собраны отдельно и заменяются при переходе к целевому продукту без изменения ядра.

Детальные требования к поведению ведутся в спецификациях проекта; этот документ фиксирует продукт, границы работ и модель угроз.
